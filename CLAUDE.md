# head-hunter-hunter

Локальное приложение для массовых автооткликов на hh.ru через Playwright.
Без деплоя, один пользователь, запускается вручную на машине владельца.

Полный ресёрч с источниками: `.claude/RESEARCH.md` — читать перед архитектурными
решениями. Этот файл — рабочая память проекта: договорённости, подтверждённые факты
и грабли, на которые уже наступили.

---

## Цель и её следствия

**Цель — максимум откликов.** Это не метафора, а критерий для каждого решения.
Владелец несколько раз разворачивал предложенные ограничения именно по этой причине.
Прежде чем добавлять любую разборчивость, проверь, не противоречит ли она цели.

Что из этого следует, и что НЕ надо «улучшать» обратно:

- **Фильтров по зарплате, опыту, формату работы и региону нет.** Были — убраны как
  пришедшие из шаблона, а не из задачи. Сужение по обсуждаемым критериям стоит откликов.
- **Единственный фильтр — «фронтенд ли это вообще».** С 18.09 в `scoring.keywords`
  и в строке поиска добавлены `fullstack`/`фулстек`/`node`/`nest`: у владельца есть
  коммерческий бэкенд на Node.js, NestJS и PostgreSQL, поэтому фуллстек-вакансия —
  это отклик, а не мимо. Сужать обратно — терять очередь.
- **Маршрутизация никогда не отказывает.** Была логика «при неоднозначности пропускаем» —
  развёрнута. Vue-резюме уходит только когда вакансия явно про Vue; всё остальное,
  включая «React / Vue» и вакансии без стека, идёт на react как фолбэк.
- **LLM-скоринг вакансий сознательно не делается.** Он служит отсеву, то есть работает
  против цели. Код заготовлен (`scores`, веса в конфиге), но не подключён.
- **Раздела «чего нет в резюме» в файлах резюме нет.** Был — убран: отсутствие в резюме
  не означает отсутствия опыта, резюме это отредактированный документ.

## Инварианты — нарушать нельзя

1. **Все селекторы hh живут в `src/hh/selectors.ts`.** Ни одного CSS-селектора больше
   нигде. Каждый — массив кандидатов, пробуем по порядку: hh держит несколько вёрсток
   одновременно (A/B, раскатка по регионам).
2. **Капчу не решаем.** Никаких 2captcha/anti-captcha. Увидели — остановились, позвали
   человека (`HumanNeededError`). Автоматическое решение превращает временный бан
   в постоянный.
3. **Пароль hh нигде не хранится.** Вход только руками через `npm run login`, сессия —
   в persistent Chromium profile. Не добавлять поля логина/пароля в конфиг.
4. **Лимит откликов — скользящее окно 24ч**, не календарные сутки. Считать только по
   `applications.applied_at`. Счётчик «сброс в полночь» рассинхронизируется с hh.
5. **Успех отклика подтверждается по DOM, а не предполагается.** Ложный `applied` стоит
   дважды: живая вакансия навсегда выпадает из очереди и занимает слот в окне, который
   hh не считал.
6. **API hh.ru закрыт полностью** (и отклики, и поиск). Не писать код против `api.hh.ru`.
7. **Скриншот на каждую ошибку.** Упавший селектор иначе не отладить постфактум.
   Автоповторов неуспешных откликов нет: повторы по кругу против hh превращают
   сломанный селектор в заблокированный аккаунт. Возврат в очередь только вручную.
8. **Никаких фиксированных пауз.** Только рандомизированные (`pause`, `randomBetween`).
9. **Вакансии с вопросами работодателя и тестовыми НЕ откликаем.** Ответы на вопросы —
   свободный текст, который должен писать человек; сгенерированный ответ хуже, чем его
   отсутствие, потому что выдаёт бота там, где работодатель проверяет обратное.
   Статус `needs_human`, очередь `npm run review`, лимит не тратится.
10. **Резюме выбирает вакансия, а не конфиг.** Совпадение в заголовке весит в 5 раз
    больше, чем в теле: «Vue-разработчик, React будет плюсом» — это Vue-вакансия.
11. **Пропуск — это НЕ запись в `applications`.** Очередь исключает вакансии с откликом
    любого статуса, поэтому строка, поставленная «просто чтобы отметить», выкидывает
    живую вакансию навсегда. Наступали дважды: неодобренное письмо и отсутствующее
    письмо оба писали `skipped`. Записывать только то, что реально произошло на hh.

## Как работает пайплайн

```
collect:  выдача hh → парсинг карточек → хард-фильтры → маршрутизация
          по заголовку → SQLite. Ничего не отправляет.

apply:    (в llm-режиме сначала письма на те же вакансии — см. ниже) →
          очередь → страница вакансии → клик «Откликнуться» →
          classifyApplyFlow → модалка? → выбор резюме → письмо →
          отправка → подтверждение по DOM → запись в applications
```

Очередь (`pendingVacancies`) исключает вакансии с откликом **любого** статуса и
сортирует: сначала те, где в карточке была кнопка отклика, потом по `hh_id` убывающе
(свежие объявления имеют большие id).

## Сопроводительные письма

Два режима, `letter.mode`:

- **`static`** — один текст из `letter.text` на все отклики. Ни генерации, ни чтения
  описаний, ни одобрения. Отклик ни от чего не зависит.
- **`llm`** (сейчас) — письмо под каждую вакансию.

**Письма пишутся внутри прогона откликов, а не отдельным шагом.** `runApplications`
в начале берёт свои кандидаты, отбирает тех, у кого письма нет, и вызывает
`writeLettersFor` — тот же код, но на точный список, а не на собственную выборку
(`vacanciesNeedingLetters` расходится со списком откликов, как только у части вакансий
письмо уже есть). Одна кнопка вместо двух: письмо — часть отклика, а отдельный шаг,
который надо не забыть, забывается, и отклик уходит пустым.

Всё равно пачкой, а не письмом на вакансию внутри цикла: каждый вызов `claude -p`
заново шлёт системный промпт Claude Code, замер даёт 24-кратную разницу. Трафик к hh
от этого не меняется — страницы вакансий читаются один раз за описаниями, ровно как
их читал отдельный прогон писем.

**Вакансия без письма пропускается и остаётся в очереди.** Раньше отклик уходил без
сопроводительного и молча. Записи в `applications` при этом нет — строка любого
статуса выкинула бы живую вакансию из очереди навсегда. Если генерация стабильно
падает, прогон просто ничего не отправит, и это видно в логе.

Кнопка «написать письма» и `npm run letters` остались: они нужны, только если хочется
написать письма заранее и прочитать их до отклика — читаются они во вкладке «очередь».

### Правила письма — это правила владельца, не общий совет

Промпт (`letters/prompt.ts`, `PROMPT_VERSION = 'v3'`) перенесён с того, которым
владелец пользовался руками в claude.ai. Каждое правило продиктовано им, «улучшать»
их в сторону обычного «напиши хорошее письмо» не надо:

1. **Письмо должно читаться написанным человеком.** Практически это правило про
   типографику: длинное тире — главная улика, его никто не набирает на клавиатуре.
   Запрещены `— – … « » “ ” •`, эмодзи, неразрывные и тонкие пробелы. `tidyLetter`
   чинит (меняет на `-`, `...`, `"`, обычный пробел), `validate.ts` ловит остаток
   (`typography`). По той же причине зарплата форматируется как `200 000 руб`, без
   тонкой шпации и знака ₽.
2. **Мотивация, а не универсальный текст.** Зацепка за 1-2 конкретные детали вакансии.
3. **Кратко.** Лимит 700 символов (с 23.09; было 1000), цель — 60% от него, то есть
   420, 3-5 предложений. Цель и порог «провал задачи» считаются от `maxChars`
   в `prompt.ts`, поэтому лимит тянет за собой и их. Замер на живых
   вакансиях: с формулировкой «потолок N, цель M» модель писала ~820 знаков, с
   «цель M, длиннее M+100 — провал задачи» — 540-670. Потолок модель читает как цель.
4. **Никогда не признаваться в пробеле.** Ни «не работал с», ни «быстро освою», ни
   «не пугает», ни «без прямого опыта» — технологию, которой нет в резюме, просто не
   упоминаем. Ловится как `self_deprecating`. Первый же прогон дал «фуллстек-часть не
   пугает» и «даже без прямого опыта на Python», поэтому проверка формулируется
   шире, чем «нет опыта».
5. **Без подписи и контактов.** Письмо идёт вместе с резюме, там и имя, и телефон.
   `signature` срабатывает на «С уважением, Имя» и на почту/телефон/телеграм;
   «отношусь с уважением к продукту» — не подпись, поэтому за сигналом требуется
   слово с большой буквы.
6. **Приветствие «Здравствуйте!»**, без обращения по имени — имени мы не знаем.

Отбракованное письмо не сохраняется (в БД оно выглядело бы одобряемым), поэтому
`validateLetter` возвращает `matched` — фрагмент текста, который сработал, и лог пишет
его цитатой: «признаётся, что чего-то не знает — „фуллстек-часть не пугает даже без
прямого опыта"». Без цитаты вердикт нечем проверить: текста уже нет. Полный текст
уходит в `log.debug`. Тот же принцип, что у детекторов hh.

`letter.extraSkills` — опыт сверх резюме (бэкенд: Node.js, NestJS, PostgreSQL,
Prisma), он подклеивается к резюме в промпте. Именно в конфиг, а не в `resume.*.md`:
те файлы повторяют PDF, который реально прикладывается к отклику, и должны ему
соответствовать.

`letter.requireManualApproval` — `false` по умолчанию и в конфиге: письмо уходит
как написано. Одобрять при этом есть чем — во вкладке «очередь» письмо открывается,
правится и одобряется (`POST /api/letters/:id/approve`), так что включить проверку
теперь осмысленно, а не декоративно. Раньше неодобренное письмо писало в
`applications` строку `skipped` и вакансия терялась навсегда (инвариант 11); теперь
это `continue` без записи — ожидание одобрения пропуск, а не приговор.

**Лимит длины письма на hh — 10 000 символов** (снят со счётчика поля, в разметке
`maxlength` отсутствует). В конфиге 700 — столько назвал владелец: письмо на 10 000
знаков никто не читает.

### Как устроена генерация

- **Генерировать только пачками.** Каждый вызов `claude -p` заново отправляет системный
  промпт Claude Code (~20-27k токенов) независимо от нагрузки. Замеры: одно письмо —
  $0.041, пачка из десяти — $0.0017 за письмо. Разница в 24 раза, и она важнее выбора
  модели. Это не деньги: `total_cost_usd` от CLI — справочная величина, расходуется
  квота подписки.
- **Формат ответа — разделители `###ПИСЬМО N###`, не JSON.** У писем есть абзацы,
  перевод строки внутри JSON-строки невалиден, падала вся пачка.
- **Зарплаты и ссылок в письме нет никогда — и вакансию про них не разбираем.**
  Было наоборот: `letters/requirements.ts` искал в описании просьбу назвать вилку или
  дать GitHub, `scoring/grade.ts` подбирал сумму из `letter.salaryByGrade`, а для
  вакансий без просьбы в промпт клался явный запрет. Разбор ошибался в обе стороны и
  молча: «Выкат: **GitLab CI**» в описании стека читался как просьба дать ссылки
  (137342018 — письмо с абзацем про NDA), «**уровень дохода** обсуждаем по итогам
  технического интервью» — как просьба назвать вилку (137343275 — письмо с «рассматриваю
  200 000 руб»). Владелец свернул всю механику: деньги обсуждаются на созвоне, ссылки
  присылаются по запросу, в письме этих тем нет, даже когда вакансия прямо просит.
  `requirements.ts`, `grade.ts`, `letter.salaryByGrade` и `letter.noLinksExcuse`
  удалены. Запретов взамен тоже нет — ни в промпте, ни в `validate.ts` (`unsolicited_salary`
  и `unsolicited_links` убраны вместе с ними): владелец отдельно поправил, что ограничений
  в промпте быть не должно. Про зарплату и ссылки промпт просто молчит, и модель сама
  почти никогда о них не заговаривает.
  **Не возвращать ни разбор описания, ни запреты.** Разбор ошибался молча, а запрет —
  это лишняя строка в промпте ради темы, которой и так нет.

## LLM

Подписка Claude Code — **не** API-ключ. Провайдер `claude-cli` вызывает локальный
авторизованный бинарь `claude -p`; ключа на машине нет и не нужно.

## Грабли, на которые уже наступили

Все четыре класса ошибок дали молчаливые баги: код работает, просто делает не то.

### 1. Кириллица в регулярках

**`\w`, `\b`, `\d` в JavaScript работают только по ASCII.** За сессию всплыло четырежды:
`/^\s*до\b/` не срабатывал на «до 250 000» и зарплата читалась как нижняя граница;
`ссылк\w*` не совпадало со «ссылки»; `ожидани\w*` — с «ожидания»; `^[-*]\s+\w` не ловил
markdown-списки на русском.

Использовать `\p{L}` с флагом `/u`. Любую регулярку с русским текстом покрывать тестом.

### 2. Детекторы: три правила

Выведены из трёх ложных срабатываний, каждое из которых останавливало работу.

1. **Проверять видимость, а не существование.** hh держит в DOM невидимый iframe капчи
   и схлопнутые предупреждения (`hidden-resume-warning`, `max-height: 0`).
   `firstVisibleMatch`, не `firstMatch`.
2. **Ограничивать область поиска.** Признаки вопросов работодателя искать внутри формы
   или диалога (`hasWithin`), а не по документу: в описании вакансии «тестовое задание» —
   рассказ о процессе найма.
   **Но область надо брать правильную: `form` первой на странице идёт форма поиска
   в шапке hh** (`action="/search/vacancy"`). `page.locator('form').first()` хватал её,
   вопросы работодателя не находились, и все такие вакансии падали в `unrecognised_form`.
   На `/applicant/vacancy_response` область — `main form`, затем `main`. Описания
   вакансии на этой странице нет, поэтому `main` здесь безопасен.
   Симптом, по которому это ловится: дамп `data/probe/needs-human-*.html` содержит
   форму поиска вместо формы отклика.
3. **Текстовые признаки антибота — только на странице без интерфейса hh**
   (`looksLikeHhPage`). «DDoS-Guard» на живой выдаче — это название компании-работодателя.

Общее: каждый детектор, который останавливает работу, обязан логировать сработавший
селектор. Сообщение «captcha» без имени селектора неотлаживаемо.

### 3. tsx + Playwright

**Внутри `page.evaluate` / `evaluateAll` нельзя присваивать функции в `const`.**
tsx собирает с esbuild `keepNames`, который переписывает `const f = () => {}` в
`__name(() => {}, "f")`. Колбэк выполняется в браузере, где хелпера нет — прогон падает
посреди работы. Только инлайн-выражения. В `browser.ts` есть шим-страховка, но полагаться
на неё нельзя.

### 4. Знание против незнания

Отличать «нет» от «неизвестно». `has_test` с карточки ставится в `true` или `null`,
никогда в `false`: карточка доказывает наличие теста, но не его отсутствие, а `false`
не даст позднему разбору страницы заполнить флаг (`COALESCE` примет его за знание).
`can_apply_from_list = NULL` сортируется вместе с пригодными, а не последним.

## Что подтверждено на живом hh

Разведка (`npm run selectors:probe`) и боевой прогон.

- **Выдача:** `vacancy-serp__vacancy` (50 на странице), `serp-item__title`,
  `vacancy-serp__vacancy-employer`, `vacancy-serp__vacancy-address`,
  `vacancy-serp__vacancy_response`. Пагинация ссылками `pager-page`, кнопки «вперёд»
  нет — ходим по `&page=N`.
- **Два потока отклика:** модалка (`div[role="dialog"]`, автоматизируем) и отдельная
  страница `/applicant/vacancy_response` с вопросами или тестовым (не автоматизируем).
- **Модалка:** `add-cover-letter` раскрывает поле письма — **до клика его нет в DOM**.
  `vacancy-response-popup-form-letter-input`, `vacancy-response-submit-popup`.
- **Дропдаун резюме:** `div[role="button"]` с `[data-qa="resume-title"]` внутри. Пункты —
  радио-список `[data-qa="cell"]` в портале **вне** модалки, у каждого
  `input[type=radio]` со стабильным id резюме.
- **Предупреждение «Вы откликаетесь на вакансию в другой стране»** встаёт между кнопкой
  «Откликнуться» и формой отклика: диалог без `role="dialog"` с кнопками «Все равно
  откликнуться» / «Отменить». `apply.modal` его не ловил, и вакансия падала в
  `blocked` → `unknown_state` (137448033, 18.09). Подтверждаем всегда
  (`confirmOtherCountry`, `selectors.apply.confirmOtherCountry`) — география это не
  повод звать человека, отказ работодателя дешевле неотправленного отклика. Дальше
  идёт обычный поток: модалка или страница отклика.
- **`hidden-resume-warning`** лежит в DOM всегда (схлопнут) — проверять только видимость.
- **Классы `magritte-*___hash` хешированные**, опираться нельзя.
- **Успех отклика:** «Отклик отправлен» / «Резюме доставлено» — подтверждено в бою.
  Обе формы ловит одна регулярка `(Отклик|Резюме) (отправлен|доставлен)[оа]?`. До 17.09
  в селекторах стояло «Резюме отправлено», и живой отклик с «Резюме доставлено»
  записался как неуспешный: факт был записан здесь, но в `selectors.ts` не доехал.
  Запись в этом файле — не замена селектору.

- **Капча приходит ПОСЛЕ кнопки «Отправить», без перехода** — диалог «Пройдите капчу»
  с картинкой и полем ввода поверх модалки отклика. Прогон 22.09: 14 откликов ушло,
  на 15-м встала капча, и дальше 63 вакансии подряд легли в `no_success_confirmation`
  за 34 минуты. Причина не в подтверждении успеха: `applyToVacancy` капчу не проверял
  вовсе, а `goto` ловит состояние только при навигации — здесь навигации нет.
  Теперь `waitOutCaptcha` стоит после клика «Откликнуться», после «Отправить» и в
  `goto` (там — только если передан `cfg`; передают apply, collect и чтение описаний
  для писем). **Капчу по-прежнему не решаем — ждём человека:** браузер headful и уже
  открыт на капче, владелец вводит её руками, а код опрашивает DOM, пока она не
  исчезнет, и продолжает тот же отклик. Разница между временной проверкой и баном —
  в том, кто нажимает клавиши, поэтому именно эта часть не автоматизирована
  (инвариант 2 в силе). Ждём до `browser.manualActionTimeoutMs` (20 минут — 5 не хватало, чтобы дойти
  до клавиатуры, а прогон, сдавшийся раньше, выбрасывает недоделанную очередь);
  не дождались или headless — `HumanNeededError`, прогон встаёт, строка в
  `applications` НЕ пишется, вакансия остаётся в очереди (инвариант 11).
  Клик, поднявший капчу, не проходит, поэтому после неё он повторяется: «Откликнуться»
  жмётся снова, если форма так и не открылась, а «Отправить» — только если не видно
  подтверждения успеха. Это не автоповтор неуспешного отклика (инвариант 7), а
  завершение прерванного; на дубль hh отвечает «вы уже откликались», и это дешевле
  потерянной вакансии. Детектор ищет видимую капчу среди всех
  совпадений, а не `.first()`: скрытый iframe капчи лежит в DOM всегда и перекрывал бы
  видимую. Текстовые признаки (`captchaText`) — только внутри оверлея (`captchaScope`),
  под модалкой лежит описание вакансии. Живого DOM капчи нет, атрибутные кандидаты
  сняты со скриншота — поэтому `no_success_confirmation` теперь дополнительно
  сохраняет HTML в `data/probe/`, чтобы селектор было чем чинить.
  Почему hh её показал — не выяснено; гипотеза про темп (100/час при рекомендованных
  ресёрчем ~5) не проверена.

## UI (этап 8)

`npm run dev` поднимает Fastify на `127.0.0.1:3000` и Vite на `5173`; Vite проксирует
`/api`, поэтому SSE, картинки и запросы живут на одном origin.

Вкладки: дашборд · очередь · ручные · неуспешные · история · конфиг. Плюс постоянная
панель живого лога справа.

Решения, принятые здесь, и причины — их же не надо «улучшать» обратно:

- **Прогоны запускаются из UI** (`собрать вакансии`, `откликнуться ×n`, `письма`,
  `проверить сессию`) и идут **в процессе сервера**. Иначе живой лог не имеет смысла:
  `logBus` — шина процесса, и прогон, запущенный из CLI в другом процессе, до SSE
  не доходит.
- **Один прогон за раз, замок в `runner.ts`.** Два прогона делят один persistent-профиль
  Chromium — это две вкладки, гоняющие одну сессию hh, ровно та форма трафика, которая
  выглядит автоматизированной. Второй запуск получает 409.
- **Запуск отвечает сразу**, не дожидаясь конца: работа идёт минутами, прогресс уходит
  в SSE, итог оседает в `lastRun` и показывается на дашборде.
- **Кнопки входа в hh нет и не будет** — инвариант 3, пароль не хранится. Когда профиля
  нет, UI говорит запустить `npm run login`.
- **Конфиг из UI не правится — кроме `dryRun`, `search.text`, `letter.mode` и
  `letter.text`.** Переключатель режима живёт в шапке (`POST /api/config/dry-run`),
  остальное — в «настройках прогона» на дашборде (`POST /api/config/search-text`,
  `POST /api/config/letter`). Все пишутся одной функцией `patchConfig` в `config/save.ts`. Запись идёт через ту же `configSchema`,
  что и загрузка, поэтому второго валидатора нет; в файл кладётся исходный объект
  пользователя с одним изменённым ключом, а **не** результат парсинга — иначе в конфиг
  впечатались бы все умолчания zod и утонули те несколько настроек, которые владелец
  выбрал сам. Пишется через временный файл и `rename`, чтобы прерванная запись не
  оставила обрезанный конфиг. Переключение во время прогона отклоняется (409): прогон
  уже прочитал конфиг на старте. Включение боевого режима спрашивает подтверждение,
  возврат к пробе — нет. Смена строки поиска во время прогона тоже отклоняется (409):
  collect уже собрал свой URL. Остальные настройки остаются правкой файла.
  Сервер перечитывает `config.json` перед каждым прогоном (`loadConfig(true)`).
  Строка поиска правится из UI потому, что именно она определяет, сколько вакансий
  вообще есть в очереди, — расширение запроса это самый дешёвый способ добрать отклики.
  Текст письма и режим — по той же причине: это содержимое самого отклика, а не настройка
  окружения. Переключение в `llm` из UI ничего не генерирует прямо в момент переключения,
  но и готовить ничего не надо: письма напишет ближайший прогон откликов.
- **В «настройках прогона» показывается только то, что меняют.** Регион, период и число
  страниц убраны (все три и так нефильтрующие умолчания), список резюме тоже — маршрутизация
  его не спрашивает у человека. Пути к конфигу и профилю убраны оттуда же: путь к конфигу
  и так стоит над вкладкой «конфиг», а профиль нужен раз в жизни, при `npm run login`.
  `CopyPath` остался на вкладке «конфиг».
- **Карточки дашборда: одна цифра на вопрос.** «Отправлено за 24ч» и «можно сейчас»
  свёрнуты в `лимит за 24ч` со значением `6/100` — вопрос всегда «сколько осталось»,
  и он читается только из отношения. Карточка «за час» убрана: часовой лимит по-прежнему
  проверяет `rateLimiter`, а когда он блокирует, об этом говорит кнопка отклика.
  «Неуспешные» красная всегда, даже на нуле — эту очередь никто не разгребает сам.
  Плашки «боевой режим» на дашборде нет: режим видно по переключателю в шапке, а
  повторять это над карточками незачем. Пробные прогоны лежат отдельным статусом
  `dry_run`, в счётчики откликов и в лимит 24ч не попадают (`countAppliedWithin`
  фильтрует `status = 'applied'`) и показываются подписью под карточками.
- **Вкладка «конфиг» показывает сам файл** (`raw` из `GET /api/config`), а не разобранный
  объект: парсинг подставляет все умолчания zod, и на экране оказывалось не то, что
  написано в файле. Пояснительная плашка и предупреждения `limitWarnings` с вкладки убраны —
  лимиты владелец поднял сознательно, и повторять это на каждом открытии незачем.
- **Дашборд не ходит в hh.** Все счётчики — из БД и конфига. Иначе открытый в фоне UI
  генерировал бы простоем больше трафика, чем сами отклики. Проверка сессии — отдельная
  кнопка (тот же один запрос, что и в `doctor`).
- **Письмо читается во вкладке «очередь», до отправки** — колонка «письмо», кнопка
  «открыть», в модалке текст в `textarea`: можно поправить и одобрить одной кнопкой
  («сохранить и одобрить», `POST /api/letters/:id/approve`, `repo.approveLetter`
  помечает строку `edited`). Отдельной кнопки «сохранить» нет: правка без отправки —
  это потерянная правка. Во время прогона одобрение отклоняется (409) — прогон читает
  письма по ходу, и одобренное на середине либо не попадёт в отклик, либо уйдёт версия,
  которую никто не видел. Показывается только в llm-режиме.
- **Карточка писем на дашборде называется по настройке.** При выключенном одобрении
  она «писем готово» с подписью «уйдут с ближайшим откликом»: счётчик считает письма
  без `approved_at`, но ждать их нечему, и слово «на одобрении» отправило владельца
  искать экран одобрения, которого не было.
- **В истории есть колонка «письмо»** — кнопка «открыть» и модалка с текстом, который
  ушёл с этим откликом (`applications.letter_id` → `letters.text`, LEFT JOIN в
  `applicationHistory`). У откликов из static-режима там прочерк: тот текст живёт в
  конфиге и в строку не копируется. Модалка (`common.tsx`, `Modal`) закрывается по
  Escape и по клику мимо карточки; клик по самому тексту не закрывает — иначе письмо
  нельзя выделить. Escape и блокировка скролла вынесены в `useDismiss`, общий с
  `Lightbox`: оверлей, который закрывается мышью, но не клавишей, — это ловушка.
- **Скриншоты отдаются только по имени файла**, путь всегда резолвится внутрь
  `data/screenshots`: в БД лежат абсолютные пути, и отдать такой путь прямо в чтение
  файла — значит превратить просмотрщик в «прочитай что угодно на диске».
- **У «ручных» есть «разобрал все (N)»** рядом с чекбоксом «показывать разобранные».
  Очередь из двадцати — это двадцать кликов, а очередь, которую дорого разгребать,
  перестают читать. Спрашивает подтверждение: вернуть вакансию в эту очередь из UI
  нечем. Штампует только неразобранные — повторный штамп сдвинул бы дату у разобранных
  раньше и потерял, когда с ними реально разобрались.
- **Возврат неуспешных в очередь — кнопка, но по-прежнему ручной** (инвариант 7):
  причина обычно в сломанном селекторе, и автоповтор превращает её в блокировку.
- **Сервер слушает только `127.0.0.1`.** Один POST отправляет реальные отклики от имени
  залогиненного пользователя; такое не выставляют в сеть.

`npm run build:ui` собирает бандл в `data/ui-dist` — проверка, что код не завязан на
dev-режим. Статику сервер пока не раздаёт, рабочий режим — `npm run dev`.
