# hh.ru Auto-Apply: ресёрч и техническая документация

> Локальное веб-приложение для автооткликов на hh.ru через Playwright.
> Без деплоя, для личного использования, без платных сервисов.
>
> Дата ресёрча: **2026-09-17**. Источники и методика — в конце документа.
> ⚠️ Вся фактура сильно времязависима: вёрстка hh, антибот и API меняются. Перед реализацией каждый селектор и каждый эндпоинт проверять заново.

## 1. Официальный HH API — почему не подходит

### 1.1 Что установлено

- Все методы с пользовательской авторизацией требуют регистрации приложения на dev.hh.ru и OAuth 2.0 (`Authorization: Bearer <token>`).
- `grant_type=password` **отключён** — возвращает `unsupported_grant_type`. Логин/пароль напрямую обменять на токен нельзя.
- **15 декабря 2025 hh.ru закрыл публичный API для соискателей.** Работодательский/HR-контур остался. Профильные репозитории прямо мотивируют этой датой отказ от API в пользу браузера.
- Анонимный доступ к `api.hh.ru` уже режется: `GET /vacancies` без токена отдаёт `{errors:[{type:"forbidden"}]}`, а с небрендированным `User-Agent` — `bad_user_agent`.

**Оговорка (важная):** официального changelog от hh.ru получить не удалось — факт закрытия подтверждён вторичными источниками (Habr ×3, пост hh.ru в setka.ru, podustal.ru) плюс мотивировкой в README репозиториев. По одному источнику, **сертифицированные OAuth-интеграции не пострадали** — то есть «закрыт для всех» это упрощение. Утверждение «откликаться можно через `POST /negotiations`» было **дважды отклонено** верификаторами (голоса 0-3 и 1-2).

### 1.2 Антипаттерн: декомпилированные креды

Проект `s3rgeym/hh-applicant-tool` декомпилировал официальное Android-приложение hh и вытащил `CLIENT_ID`/`CLIENT_SECRET`, чтобы обойти ручную модерацию. Поддерживает email/телефон+пароль, одноразовый код, автообновление токена (~2 недели на access token).

**Не использовать.** Причины: (а) это краденые захардкоженные креды, отзываемые в любой момент; (б) сам автор фиксирует, что `grant_type=password` уже перестал работать; (в) после декабря 2025 работоспособность соискательских методов этим путём не подтверждена.

### 1.3 Что из API всё равно полезно

API остаётся **моделью предметной области**, даже если исполнять всё через DOM:

- **OpenAPI-спека** — актуальный источник параметров: `https://api.hh.ru/openapi/redoc` (человеческая), `https://api.hh.ru/openapi/specification/public` (машиночитаемая; `/openapi/openapi.json` — 404). Markdown-доки в `hhru/api` **опустошены**, там только баннеры «метод доступен в OpenAPI».
- **Таксономия ошибок отклика** (`docs/errors.md`, строки 279-283) — это карта состояний, которые надо распознавать и в DOM:

  | Ошибка | Код | Что значит для UI |
  |---|---|---|
  | `limit_exceeded` | 400/403 | Суточный лимит исчерпан → стоп до завтра |
  | `empty_message` | 403 | Письмо обязательно, а мы прислали пустое |
  | `too_long_message` | 403 | **У письма есть жёсткий лимит длины** |
  | `application_denied` | 403 | Отклик отклонён |
  | `already_applied` | — | Дедупликация не сработала |
  | `test_required` | — | Вакансия с тестовым заданием |
  | `resume_visibility_conflict` | — | Резюме скрыто/невидимо |
  | `wrong_state` | — | Вакансия архивна/недоступна |

- **Параметры поиска** `GET /vacancies` (45 штук в живой спеке). Ключевые: `text`, `search_field`, `experience`, `professional_role` (**единственное число**, не `professional_roles`), `area`, `order_by`, `period`, `excluded_text`, `work_format`, `page`, `per_page` (**max 100**). ⚠️ `schedule` помечен **deprecated** — заменён на `work_schedule_by_days`.
- **Структура вакансии.** В коротком представлении уже есть `has_test`, `response_letter_required`, `response_url`, `apply_alternate_url`, `archived`. Эти же поля воспроизводимы при парсинге DOM.
- **Post-apply workflow** — список откликов, просмотр, скрытие, чтение/отправка/редактирование сообщений. Готовая схема сущностей для SQLite.

### 1.4 Гибридной схемы не будет

Изначально рассматривался гибрид «API для поиска вакансий + Playwright только для клика «Откликнуться»» — он бы втрое сократил объём хрупкого DOM-кода.

**Этот путь закрыт: API hh.ru закрыт полностью** (подтверждено владельцем проекта, 2026-09-17). Не только соискательские действия, но и поиск вакансий. Ресёрч фиксировал это как открытый вопрос — вопрос снят.

**Следствие для архитектуры:** весь сбор вакансий идёт через парсинг DOM поисковой выдачи. Это значит:

- Поверхность хрупкого кода вдвое больше, чем в гибридном варианте: селекторы нужны и для карточек выдачи, и для формы отклика.
- Нет готового JSON — `has_test`, `response_letter_required`, зарплату, регион придётся вытаскивать из разметки, и часть флагов может быть недоступна до открытия страницы вакансии.
- Пагинация и троттлинг ложатся на браузер — сбор 300 вакансий это 300 навигаций, а не 3 API-запроса. Закладывайте время и паузы.
- `selectors.ts` становится ещё критичнее (см. §7.4).

**Что из API остаётся полезным** — только как модель предметной области (см. §1.3): таксономия ошибок и структура сущностей. Исполнять всё придётся через DOM.

## 2. Аутентификация и антибот

### 2.1 Подтверждённый паттерн

Три независимых проекта сошлись на одном решении:

```
Однократно:  headful-браузер → пользователь вводит пароль,
             SMS/email-код и проходит капчу руками
Дальше:      сессия переиспользуется во всех запусках
```

Два способа хранения сессии:

| Способ | Как | Кто использует |
|---|---|---|
| `storageState` JSON | `context.storageState()` → файл, атомарная запись через `os.replace` | cheltaxi-lgtm/hhru |
| **Persistent profile** ✅ | `chromium.launchPersistentContext('data/session/profile', {locale:'ru-RU'})` | hh-ru-apply, otklik |

**Рекомендация — persistent profile.** Формулировка otklik: профиль в `~/.otklik/`, «чтобы hh не видел новое устройство каждый раз». Persistent context сохраняет не только cookies, но и localStorage, IndexedDB, отпечаток профиля — hh видит один и тот же браузер, а не новую машину при каждом запуске.

### 2.2 Капча и антибот

Консенсус ниши, дословно из otklik README:

> «When a captcha appears the app stops and calls you over. No 2captcha, no anti-captcha: solving them automatically is a fast way to turn a temporary block into a permanent one.»

Реалистичная позиция:

- ✅ **Headful по умолчанию**, headless — opt-in флаг, не дефолт.
- ✅ **Минимальный stealth-патчинг** через init-script: `navigator.webdriver → undefined`, `window.chrome = {runtime:{}}`. (Заметьте: cheltaxi это делает, хотя README заявляет обратное — утверждение «никакого обхода» было отклонено верификаторами 1-2.)
- ✅ **Рандомизированные задержки**, консервативные лимиты.
- ❌ **Никаких captcha-solving сервисов.**
- ⚠️ **Гарантий прохождения DDoS-Guard в headless нет.** cheltaxi README прямо признаёт: селекторы никогда не проверялись на живом hh, потому что DDoS-Guard блокировал автоматизированный браузер.

`playwright-extra` + `stealth` плагин — вариант, но ни один из изученных проектов на него не опирается; это дополнительная зависимость с неподтверждённой эффективностью против DDoS-Guard. Начинать без него.

### 2.3 Детект «нас выкинуло»

Перед каждой сессией — health-check: открыть `hh.ru/applicant/negotiations`, убедиться что залогинены. Если нет — **не пытаться перелогиниться автоматически**, а остановиться и позвать пользователя (нотификация/экран в UI).

## 3. Поиск и релевантность

### 3.1 Воронка

```
Поисковые параметры hh  →  N сотен вакансий      (грубый фильтр, дёшево)
        ↓
Хард-фильтры локально   →  отсев archived, has_test,
                           already_applied, blacklist компаний
        ↓
LLM-скоринг             →  0-100 по нескольким шкалам
        ↓
Порог + бюджет дня      →  ~30 откликов
```

### 3.2 Хард-фильтры (до LLM — экономят токены)

- `archived == true` → drop
- `has_test == true` → drop (по умолчанию; конфигурируемо).
  ⚠️ Двойная оговорка. Первая — семантическая: `has_test` не отличает обязательный тест от опционального → возможна избыточная фильтрация. Вторая, более болезненная после закрытия API: **флаг придётся извлекать из разметки**, и если в карточке выдачи его нет, узнать про тест можно будет только открыв страницу вакансии — то есть ценой лишней навигации. Проверить на этапе 0.2.
- Уже откликались (по `vacancy_id` в SQLite) → drop
- Чёрный список компаний / стоп-слова в названии (`excluded_text` можно задать и на стороне hh)
- Формат работы / регион / зарплатная вилка — по конфигу

### 3.3 Скоринг

Схема из hh-ru-apply — три оценки 0-100 с настраиваемыми весами:

| Оценка | Что меряет |
|---|---|
| `scoreVacancy` | Релевантность самого объявления (это правда Frontend React?) |
| `scoreCvMatch` | Покрытие требований вашим резюме |
| `scoreOverall` | Стоит ли откликаться |

Веса — в конфиге (`llmScoreWeights.{vacancy,cvMatch}`).

**⚠️ Confidence: low.** Это один малозвёздный репозиторий, самоописание README, код не верифицирован, замеров качества нет. Это существующая практика, **не доказанно лучший подход**. Сравнения с TF-IDF/эмбеддингами никто не делал.

**Прагматичный план:** начать с дешёвого гибрида — ключевые слова/TF-IDF как предфильтр (отсекает явный мусор бесплатно), LLM только на выживших. Батчить по 10-20 вакансий в один запрос. Кэшировать оценки по `vacancy_id` — не переоценивать одно и то же.

## 4. Генерация сопроводительных писем

### 4.1 Провайдер

Абстракция поверх провайдера (LiteLLM-подобная) с тремя режимами:

- **Локально, бесплатно:** Ollama (`qwen2.5`, `llama3.1` — русский приемлемо)
- **Бесплатно в облаке:** OpenRouter free-модели
- **Качественно:** Claude API

Один интерфейс `generateCoverLetter(vacancy, resume, config) → string` — провайдер подменяется в конфиге.

### 4.2 Критичные ограничения

- **Длина.** Ошибка `too_long_message` документирована hh → жёсткий верхний предел существует. **Точное число в источниках не найдено** (открытый вопрос). Действие: замерить эмпирически в UI hh, зашить в конфиг с запасом, и **валидировать длину до отправки**, а не ловить ошибку после.
- **Пустое письмо** → `empty_message`, если `response_letter_required == true`. Письмо обязательно генерировать для таких вакансий.
- **Качество > объём.** Шаблонное письмо на 50 вакансий читается как спам и работает против вас. Промпт должен вытаскивать 1-2 конкретные детали из описания вакансии (стек, продукт, задача) и связывать с реальным опытом из резюме.

### 4.3 Промпт-дисциплина

- Резюме передавать структурированно (стек, годы, проекты), не сырым текстом.
- Явно запретить: выдумывать опыт, которого нет в резюме; писать общие фразы; превышать N символов.
- **Human-in-the-loop режим:** превью писем в UI перед отправкой, хотя бы для первых прогонов. Это единственный способ поймать галлюцинации до того, как их прочитает рекрутер.

## 5. Лимиты, правила и риски

### 5.1 Лимит откликов

**Первоисточник** — соглашение hh.ru об оказании услуг по содействию в трудоустройстве:

> «не более 200 раз (200 откликов) в совокупности по всем вакансиям… в течение 24 последовательных часов»

**Критичная инженерная деталь: окно скользящее, а не календарные сутки.** Локальный гейт «сбрасываем счётчик в полночь» рассинхронизируется с окном hh и приводит к отказам (issue axisrow/hhru#1142). Считать так же: rolling window по timestamp'ам в SQLite.

Вторичные источники упоминают также ~3000/месяц — первичкой не подтверждено.

### 5.2 Безопасные настройки по умолчанию

Дефолты otklik — берём как стартовую точку:

| Параметр | Значение |
|---|---|
| Откликов в день | **30** (при потолке 200) |
| Откликов в час | **5** |
| Пауза между действиями | **800 мс ± 400 мс** |
| Режим браузера | headful |
| Капча | ручная |

Плюс: не запускать в 4 утра, рандомизировать порядок вакансий, делать «человеческие» паузы на чтение страницы вакансии.

### 5.3 Правовой риск

otklik README дословно:

> «hh.ru rules formally prohibit automated applications. Using this app may get your account suspended, temporarily or permanently… Use it at your own risk and not on the hh.ru account your career depends on.»

Тот же дисклеймер независимо повторяется минимум в четырёх несвязанных проектах. Автор hh-applicant-tool прямо пишет, что не регистрировал своё приложение — регистрация проходит ручную модерацию, а автоотклики правилам противоречат, заявку бы не одобрили. **Это свидетельство против собственного интереса** (автор предупреждает о своём же инструменте), что повышает его надёжность.

**⚠️ Пробел в ресёрче:** ни один источник не цитирует конкретный пункт пользовательского соглашения. `robots.txt` не проверялся. **Сверьтесь с текстом соглашения hh.ru самостоятельно перед реализацией.**

Практический вывод: риск реален и некупируем. Способы его снизить — только поведенческие (низкие лимиты, человекоподобный ритм, качественные письма, никакого captcha-solving). Способа обнулить — нет.

## 7. Архитектура

### 7.1 Стек

```
Frontend    React + Vite + TypeScript          (localhost:5173)
Backend     Node.js + TypeScript + Fastify     (localhost:3000)
Browser     Playwright (Chromium, persistent profile)
DB          SQLite (better-sqlite3 / Drizzle)
LLM         провайдер-агностик: Ollama | OpenRouter | Claude API
Queue       in-process, последовательная, с rate-limiter
```

Почему не Next.js / не Docker: приложение локальное, одноюзерное, без деплоя. Vite dev-server + Fastify — минимум церемоний. Docker мешает persistent-профилю браузера и ручному прохождению капчи.

### 7.2 Модули

```
src/
  hh/
    selectors.ts       ⚠️ ВСЕ CSS/data-qa селекторы hh: карточки выдачи И форма отклика.
                          Единственная точка починки. Поверхность выросла — API закрыт.
    browser.ts            launchPersistentContext, init-script, health-check
    auth.ts               команда login: headful, ждём ручного входа
    search.ts             сбор вакансий через парсинг поисковой выдачи (DOM)
    apply.ts              клик «Откликнуться», выбор резюме, письмо, сабмит
    errors.ts             маппинг DOM-состояний на таксономию из §1.3
  scoring/
    prefilter.ts          хард-фильтры + дешёвый keyword/TF-IDF отсев
    llm-score.ts          батчевый скоринг, кэш по vacancy_id
  letters/
    generate.ts           промпт + генерация
    validate.ts           длина, запрещённые паттерны
  llm/
    provider.ts           единый интерфейс, 3 реализации
  db/
    schema.ts             см. 7.3
    repo.ts
  queue/
    runner.ts             последовательная очередь
    rate-limiter.ts       ⚠️ скользящее окно 24ч, не календарные сутки
  server/
    api.ts                REST для фронта
    events.ts             SSE — лайв-лог в UI
  ui/                     React: дашборд, конфиг, превью писем, история, капча-алерт
```

### 7.3 Схема БД

```sql
vacancies      id, hh_id, title, company, url, salary, area, raw_json,
               has_test, response_letter_required, found_at
scores         vacancy_id, score_vacancy, score_cv_match, score_overall,
               reason, model, scored_at
letters        vacancy_id, text, model, prompt_version, chars, created_at
applications   vacancy_id, status, letter_id, applied_at, error_code,
               screenshot_path
runs           id, started_at, finished_at, planned, applied, skipped, failed
config         key, value
```

`applications` — источник правды для дедупликации и для rolling-window лимитера.

### 7.4 Ключевые инженерные решения

- **Селекторы через `data-qa`.** hh исторически использует `data-qa` атрибуты — они стабильнее классов. Проверить наличие на кнопке «Откликнуться», селекторе резюме, поле письма.
- **Скриншот на каждый отклик** (или хотя бы на каждую ошибку) в `data/screenshots/` — единственный способ отладить упавший селектор постфактум.
- **Dry-run режим** — прогон всей воронки без финального клика. Обязателен для первого запуска и после каждого изменения селекторов.
- **Kill switch** — кнопка «стоп» в UI, останавливающая очередь между вакансиями.
- **Идемпотентность** — перед кликом ещё раз проверить БД и состояние страницы («вы уже откликались»).

## 9. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Блокировка аккаунта hh | средняя | Низкие лимиты, человекоподобный ритм, качественные письма, тестовый аккаунт для отладки |
| DDoS-Guard блокирует автоматизацию | **высокая** | Headful + persistent profile; проверить на этапе 0.5 — это go/no-go |
| Селекторы сломались после релиза hh | **высокая, регулярно** | Изоляция в `selectors.ts`, smoke-тест, скриншоты ошибок. После закрытия API поверхность риска выросла: ломаться могут и выдача, и форма отклика |
| Сбор вакансий медленный и заметный (N навигаций вместо API) | высокая | Паузы, сбор пачками за несколько заходов, кэш выдачи в БД |
| LLM выдумал опыт в письме | средняя | Валидатор + превью в UI, особенно на первых прогонах |
| Рассинхрон лимита (календарь vs скользящее окно) | высокая, если не учесть | Rolling window с самого начала |
| Шаблонные письма вредят репутации | средняя | Качество промпта > объём откликов |

## 11. Общая оговорка

Все проекты-образцы — малозвёздные хобби-репозитории, чьи README описывают **заявленную архитектуру, а не измеренную работоспособность**. Факт закрытия соискательского API подтверждён только вторичными источниками. Ни один найденный селектор не верифицирован на живом hh.

Это означает: документ выше — **обоснованная гипотеза архитектуры**, а не проверенный рецепт. Этап 0 существует именно для того, чтобы превратить гипотезы в факты до того, как вы напишете первую строчку `apply.ts`.
